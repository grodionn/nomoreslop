# Получение ресурсов и проверка следа

Читать при выборе, получении и адаптации внешнего материала, при проверке комплекта и перед закрытием решений о его применении. Каталог [source-adapters.json](source-adapters.json) дополняет [solution-sources.md](solution-sources.md): сохранены **35 входов из закладок + Awwwards**, а не 36 независимых авторов. `canonical_source` объединяет повторные входы одного провайдера. Дата проверки и `last_verified.scope` относятся к конкретному прежнему наблюдению.

## Задача, кандидаты и возврат к поиску

Рабочая единица — нерешённая задача участка: нужное свойство → подходящие источники → изученные кандидаты → выбор → получение → комплект → адаптация → текущая проверка свойства → сохранить, исправить или заменить.

Обращаться к ресурсам до новой существенной секции, компонента, flow, материала или поведения, после смены направления/стека и при потере исходного свойства. Повторно полученный актуальный комплект можно использовать: изменение отступа само по себе не требует сети. В новом проекте нужен поиск по его брифу; кеш другого бренда не задаёт его дизайн-код. Слой композиции, flow, секции, графики или фона не закрывается одним подключением библиотеки анимации.

Готовая подходящая основа применяется по умолчанию в нетривиальном новом UI; собственная реализация имеет конкретное основание после рассмотрения пригодных вариантов либо следует точному пользовательскому поручению. Один отклонённый кандидат не завершает задачу. Причина отклонения ведёт к альтернативе. Оценивать смысл и свойство результата, а не количество просмотренных сервисов.

## Что исполняется

Зависимый только от стандартной библиотеки Python 3.10+ скрипт `scripts/resource_pipeline.py` поддерживает пять команд. Примеры ниже выполняются из каталога скилла; `PROJECT_DIR`, `PACKAGE_DIR`, `STATE.json` и URL заменяются фактическими путями/адресами.

```text
python scripts/resource_pipeline.py sources
python scripts/resource_pipeline.py sources --kind section --platform web
python scripts/resource_pipeline.py sources --id aceternity
python scripts/resource_pipeline.py inspect https://ui.aceternity.com/registry/3d-marquee.json
python scripts/resource_pipeline.py fetch https://ui.aceternity.com/registry/3d-marquee.json --project PROJECT_DIR --output vendor/3d-marquee --source aceternity
python scripts/resource_pipeline.py check-package PACKAGE_DIR
python scripts/resource_pipeline.py coverage STATE.json --project PROJECT_DIR
```

- `sources [--kind KIND] [--platform PLATFORM] [--id ID]` читает локальную карту без сети. Фильтры соединяются; пустая выдача допустима. Имена типов — из `kinds` (`section`, `composition`, `flow`, `animation`, `graphic` и др.), платформ — из `platforms`.
- `inspect URL` делает один ограниченный публичный HTTPS-запрос и классифицирует полученные байты: registry source, JSON metadata, HTML, оболочка, challenge, текст, бинарный формат или ошибка доступа. HTML и кодовые блоки не извлекаются как готовые исходники.
- `fetch URL --project PATH --output RELATIVE_DIR [--source ID]` получает только выбранный JSON registry с непустыми inline `files[].content`. `--source` связывает запись с известным ID, но не удостоверяет авторство URL. `--output` — новый каталог внутри существующего проекта. Файлы сохраняются по `files[].path`; поле `target` остаётся metadata и не выбирает место записи.
- `check-package PATH` читает исходники, package metadata и, если есть, receipt. Показывает статические импорты, транзитивный локальный граф, незакрытые helper/media пути, наблюдаемые внешние пакеты, пробелы в декларациях, registry dependencies, динамические импорты, целостность получения и изменения файлов.
- `coverage STATE.json --project PATH` читает общую модель решений и проверяет структурный след перечисленных решений, текущие файлы и наблюдения. Это не универсальный сканер полноты всех продуктовых решений.

Все команды печатают JSON. Коды завершения: **0** — отчёт получен без известного блокирующего условия этой команды; **1** — доступ/получение не состоялись, либо `check-package` нашёл `gaps/unknown`, либо `coverage` содержит findings; **2** — неправильные аргументы/структура, небезопасный путь, превышенный лимит или ошибка чтения. У `inspect` ответ `metadata_only` или `spa_shell` может вернуть 0: смотреть `access` и `capabilities`. У `fetch` 0 означает сохранённые файлы и receipt, даже если вложенный `package_check` обнаружил пробелы. Это ещё не готовая интеграция.

Каталог описывает маршруты, формат и доступ, а не автоматически подключённые инструменты. Семантический поиск, авторизованный MCP/API и официальные экспорты выполняются отдельно доступным инструментом после чтения его текущей схемы. Наличие MCP-страницы, llms.txt, CLI или OpenAPI не означает, что сервер подключён или код уже получен. Скрипт их не устанавливает и не вызывает.

## Доступ, ограничения и безопасная запись

Только публичный HTTPS на стандартном порту, без credentials, fragment и распознанных token/signed query-параметров. Локальные/непубличные адреса отсекаются при проверке DNS; каждый redirect перепроверяется, не более пяти переходов. Это ограниченный клиент обычной публичной сети, не изолированный сетевой sandbox и не инструмент для приватных endpoint.

Один ответ — до 3 MiB; socket timeout — 20 секунд, прошедшее время дополнительно проверяется между чтениями. Сжатые ответы не распаковываются. Registry — до 100 файлов и суммарно 3 MiB inline-кода; URL-only записи не скачиваются рекурсивно. Все пути проверяются до создания output: запрещены абсолютные/выходящие пути, небезопасные Windows имена, дубликаты с учётом регистра, конфликт file/directory и зарезервированный `.source`. Существующий output не перезаписывается. Ошибка файловой системы во время записи может оставить неполный новый каталог: считать его неполученным и выбрать новый путь после осмотра.

401, 402, 403, 404, 429 и сетевые ошибки возвращают явный статус; challenge, login и HTML-оболочка не становятся source. Автоповторов, переключения аккаунтов, интерфейсов ради квоты, обхода оплаты/авторизации и браузерной автоматизации внешнего поиска нет. Не устанавливаются пакеты, не запускаются lifecycle scripts и полученный код, не меняются пользовательские настройки. Альтернативный официальный публичный маршрут допустим по его собственным условиям; он не превращает Pro manifest в бесплатный Pro export.

## Receipt и комплект

В новом output лежат исходные файлы и:

- `.source/response.json` — реально полученные байты ответа;
- `.source/receipt.json` — schema_version 1, requested/canonical URL, checked/fetched time, publisher ID при указании, response SHA256, content fingerprint, имена и SHA256/размеры файлов, типы/targets, package/dev/registry dependencies, author/license metadata и `source_version`, если его сообщил источник.

Версия без данных источника остаётся `null`: хеш не выдумывает release или commit. Receipt хранит статус «received; not integrated»; скрипт не переписывает его в «применено».

`receipt_integrity.status` — `missing`, `inconsistent` или `consistent_received`. Проверка сравнивает receipt с кешированными байтами/manifest/dependencies/fingerprint; затем файлы — с полученными хешами. `matches_received`, `changed_since_received` и `missing` различаются: адаптация закономерно меняет код. Даже согласованные хеши не удостоверяют автора или истинность рассказа агента: локальные файлы и receipt можно совместно подменить.

`check-package.static_status` — `gaps`, `unknown` или `no_static_gaps_observed`. Последнее означает отсутствие найденных пробелов в ограниченном статическом разборе. Декларация dependency не доказывает её установку/совместимость. Обнаруженные `registry_dependencies_to_resolve` нужно получить и проверить отдельно.

Перед применением также разобрать стили, локальные утилиты, client/server границы, aliases, media/fonts, environment, accessibility/reduced motion, права и notices. Получение Aceternity 3D Marquee при проверке 21 октября выявило импорт `motion/react` и `@/lib/utils` при отсутствии dependencies metadata: нельзя считать пустой manifest доказательством полного комплекта.

Статический скан ограничен 1 500 исходными файлами, 12 MiB исходников и 6 000 просмотренными именами. Пропускает `.git`, `node_modules`, `.source`, `.cache`, `.next`, `coverage` и symlink-каталоги. Извлечение импортов лексическое; custom aliases, template/generated imports, плагины и runtime-сборка могут требовать bundler/ручной проверки. Неисполненная условная ветка также может быть видима статически.

## Решения для coverage

Использовать общую модель `design_state.py`: `schema_version:1`, `mode:new|redesign|local`, `decisions:[]`. Общий brief и свежесть всех проектных проверок проверяет `design_state.py check`; coverage добавляет кандидатов, происхождение и путь в приложении.

Минимальный пример записи; хеши и описания заменяются фактическими текущими данными:

```json
{
  "id": "collection",
  "section": "collection-overview",
  "intent": "Сравнить доступные предметы без потери выбора",
  "state": "verified",
  "candidates": [
    {
      "id": "author-item",
      "url": "https://example.com/author/item",
      "status": "considered"
    },
    {
      "id": "alternate-item",
      "url": "https://example.com/author/alternate",
      "status": "considered"
    }
  ],
  "selection": {
    "status": "adapted",
    "candidate_id": "author-item",
    "property": "Выбранный предмет сохраняется при просмотре соседних"
  },
  "implementation": {
    "paths": ["src/components/Collection.tsx"],
    "entrypoints": ["src/main.tsx"],
    "receipt": "vendor/item/.source/receipt.json",
    "source_map": {
      "components/Collection.tsx": "src/components/Collection.tsx"
    }
  },
  "checks": [
    {
      "id": "collection-selection",
      "kind": "source_property",
      "status": "passed",
      "action": "Выбрать предмет, перейти к соседнему, вернуться",
      "observation": "Прежний выбор сохранился в текущем интерфейсе",
      "evidence": ["evidence/collection-selection.png"],
      "environment": {"method": "browser-render", "viewport": [1280, 800]},
      "files": {"src/components/Collection.tsx": "ACTUAL_CURRENT_SHA256"}
    }
  ]
}
```

`state`: `open|selected|implemented|verified|blocked`; первые, выбранные и blocked остаются незавершёнными. `selection.status`: `integrated|adapted|own_implementation|inspiration_only`. Последние два не переименовываются в интеграцию чужого кода. У `own_implementation` требуется `reason` — конкретное основание. Все завершённые варианты требуют изученного происхождения, названного свойства, существующих implementation paths, application entrypoints и текущего наблюдения свойства. Для собственного решения кандидат может быть изученной подходящей основой, от которой обоснованно отказались; такой материал хранить как considered, а отклонение конкретного варианта — отдельной записью/объяснением. Точное поручение собственной реализации отражается в basis и reason.

У каждого кандидата нужен ID и фактический URL материала. Отклонённому кандидату нужны `reason` и `alternative`; его нельзя одновременно выбрать как origin. Название провайдера и число посещений не заменяют изученный материал.

Для `integrated/adapted` допустимы **оба** маршрута provenance:

1. Наш CLI receipt + сохранённый raw response. Исходный файл можно импортировать на месте. Если он перенесён, `implementation.source_map` явно связывает путь внутри полученного пакета с текущим проектным путём. Чужой случайный валидный receipt не закрывает след.
2. Авторизованный MCP, официальный export или репозиторий автора: вместо receipt сохранить `implementation.provenance`:

```json
{
  "kind": "mcp",
  "source_url": "https://example.com/author/item",
  "source_version": null,
  "evidence": ["evidence/authorized-export.json"],
  "files": {"src/components/Collection.tsx": "ACTUAL_CURRENT_SHA256"}
}
```

`kind` принимает `mcp|authorized_export|author_repo`. Evidence здесь — существующие локальные артефакты внутри проекта; files — текущие SHA256 всех заявленных implementation paths. Сохранить фактические сведения о получении, origin/commit, формате, доступе и terms, насколько они известны. Проверка отмечает `external_self_reported`: существование файлов и совпадение хешей не аутентифицируют экспорт и не подтверждают вызов MCP. Не создавать фиктивный transcript ради поля evidence.

`checks[].status` принимает `required|passed|failed|unverified|not_applicable`. Failed и обязательные required/unverified сохраняют gap; unverified/not_applicable требуют причины. Passed требует action, observation, непустые evidence references, environment и текущие hashes files. Для source_property/property files покрывают implementation paths. Evidence обычной проверки может быть ссылкой на браузерный/внешний артефакт: coverage проверяет наличие записи, не существование/содержание такого внешнего артефакта. Получить хеши можно `design_state.py snapshot`, но snapshot не проводит наблюдение.

`coverage.structural_status`: `gaps`, `structurally_recorded`, `not_applicable`. Прямой импорт может дать `reachable_static`, однако без наблюдаемого свойства решение остаётся с gap. Нелитеральный import на проверяемом пути даёт `unknown_edges`; отсутствие статического пути — `unknown`. Ни то, ни другое не становится passed. Указанные entrypoints, динамические/условные ветки и поведение всё равно проверяются в реальном приложении. Ограниченный скан, незакрытые helper imports и декларации пакетов проверяемой ветки оставляют findings. Отдельный невыбранный кандидат с чужими импортами остаётся пробелом его комплекта в `check-package`, но не блокирует адаптацию, в которой этих импортов нет; он не становится от этого интегрированным.

Пустой decisions в new/redesign не завершает исследование. В локальной правке без нового ресурсного решения пустой массив даёт `not_applicable`. Для явного пользовательского ограничения в новом проекте допустим `resource_scope:{status:"no_external_research",reason:"...",basis:{type:"prompt|answer|delegation|project",reference:"...",text:"..."}}`: basis — фактическое указание, а не удобное объяснение пропуска. Coverage проверяет структуру этой записи, не истину полномочий/смысла.

Ни `structurally_recorded`, ни self-reported `passed` не подтверждают художественную убедительность, права, полноту решения, факт исполнения ветки или правдивость наблюдения. Если свойство потерялось, вернуть решение в open, исправить адаптацию либо сменить основу и проверить текущий результат.

## Проверка глубины отбора

Перед обычным принятием кандидата используй [протокол отбора](resource-selection.md). Receipt и наблюдение свойства реализации не заменяют предметный поиск и сравнение. `coverage` теперь отдельно возвращает `research_status` для выбранных/реализованных решений; отсутствие записей оставляет `research_missing` даже при валидном исходнике и текущих хешах.

До зависимой реализации сохрани предварительный выбор со `state:selected` и выполни `coverage` по текущему состоянию проекта. Для отбора проверь `research_status` и относящиеся `research_*` findings: записи должны быть согласованы, а содержательные условия — подтверждены изученным материалом. Общий статус на этом этапе закономерно остаётся gaps из-за ещё открытого решения (`decision_open`); это не разрешение игнорировать пробелы поиска. После интеграции и наблюдения свойства повтори относящуюся проверку. Без Python вручную проверь те же основания; недоступность скрипта не отменяет реальный поиск.

Общий профиль хранится один раз в корне состояния. Это рабочие концепты проекта, а не выдуманная таксономия провайдера:

```json
{
  "research_profile": {
    "origin": "derived",
    "basis": "Бриф и содержание: архив шести предметов, редакционная подача, сопоставление и сохранение выбора",
    "tags": {
      "style": ["editorial", "restrained typography"],
      "composition": ["image-led index", "overview and detail"],
      "ux": ["compare collection", "preserve selection"],
      "platform": ["web", "touch"],
      "material": ["six distinct objects"],
      "avoid": ["unrelated decorative geometry"]
    }
  }
}
```

`origin`: `given|derived|mixed`; `basis` — конкретное основание в задании, принятых решениях и материале. `style`, `composition`, `ux`, `platform` — непустые массивы строк; `material`, `motion`, `avoid` добавляются по применимости. Гипотеза, которую пользователь не задавал, обозначается как выведенная. Не меняй теги задним числом только для оправдания понравившегося компонента.

Внутри соответствующего `decisions[]` добавь `research`; ниже сокращённый пример структуры, а не выполненный запрос. Каждый URL, свидетельство и наблюдение заменяется фактически полученным материалом. Кандидаты `author-item` и `alternate-item` должны уже существовать в `candidates`:

```json
{
  "research": {
    "queries": [
      {
        "id": "collection-discovery",
        "source_url": "https://example.com/catalog",
        "channel": "api",
        "scope": "tag",
        "query": "Фактический запрос и поддержанные фильтры провайдера",
        "tags": ["editorial", "image-led index", "compare collection"],
        "status": "results",
        "result_ids": ["author-item", "alternate-item"],
        "evidence": ["evidence/actual-search-result.json"]
      }
    ],
    "inspections": [
      {
        "candidate_id": "author-item",
        "evidence": ["evidence/actual-item-detail.json"],
        "observations": {
          "style": "Наблюдённый рисунок набора и его отношение к принятому языку",
          "composition": "Общий индекс рядом с подробностями выбранного предмета",
          "ux": "Изученное действие и возвращение без потери выбора",
          "material": "Вместимость шести реальных предметов и длинных названий",
          "feasibility": "Прочитанный состав, условия и цена адаптации к целевой платформе"
        },
        "prior_use": {"status": "unknown"}
      },
      {
        "candidate_id": "alternate-item",
        "evidence": ["evidence/actual-alternate-detail.json"],
        "observations": {
          "style": "Фактически изученный альтернативный язык и его пригодность",
          "composition": "Последовательные полноразмерные предметы с возвратом в индекс",
          "ux": "Осмотр одного предмета крупнее, сравнение требует другого продолжения",
          "material": "Сильные стороны и ограничения на тех же шести предметах",
          "feasibility": "Совместимость и стоимость именно этой основы"
        },
        "prior_use": {"status": "other_project", "reference": "Доступная запись прежнего проекта", "reason": "Основание повторной квалификации по текущему брифу"}
      }
    ],
    "comparison": {
      "alternative_ids": ["alternate-item"],
      "choice_reason": "Почему выбранная конструкция решает текущую задачу лучше",
      "tradeoffs": "Что выигрывает альтернативный вариант и чем платит выбранный",
      "structure_difference": "Обзор с соседней деталью против последовательного осмотра"
    },
    "closure": {"status": "compared"}
  }
}
```

`queries`: точный `source_url`, `channel:mcp|api|cli|http|search`, использованные запрос/фильтры, связанные **канонические теги проекта**, реальная выдача/ошибка и её свидетельство. Перевод тегов в названия провайдера отражается в `query`; не требуется буквальное совпадение текста запроса с русским брифом. Связанные `tags` должны относиться к положительным тегам текущего профиля, а не к произвольному popular-ярлыку. `refines` при наличии ссылается на ID предыдущего фактического запроса и объясняется полезным уточнением в рабочей записи.

`scope`: `tag|category|semantic_search|targeted_search|registry_index|exact_item|homepage|featured`. Последние три могут обнаружить материал, но сами не закрывают предметное теговое исследование. Команда `sources --kind/--platform` выбирает локальные маршруты; она не создаёт `scope:tag` и не выполняет внешний поиск. Нет универсальной команды `--tag` для всех сайтов.

`status`: `results|empty|blocked|planned`; результаты содержат `result_ids` действительных кандидатов. Для выполненного обращения нужны фактические `evidence`; пустой ответ и блокировка не превращаются в успех. План не удовлетворяет выполненному поиску. Не подставляй названия после выбора ради заполнения результата.

`inspections` связывает внутреннее изучение кандидата с отдельными наблюдениями о стиле, композиции, UX, материале и выполнимости. `prior_use.status`: `new|same_project|other_project|unknown`; известное прежнее использование требует `reference`, другое прошлое изделие — также `reason` повторной пригодности. Не сканируй чужую историю и не придумывай принадлежность: при отсутствии сведений используй unknown.

Обычный `compared` требует тематического поиска и изученной отличающейся альтернативы для той же задачи до принятия победителя. Цветовая версия или зеркало той же основы не являются структурной альтернативой. Одну изученную основу можно применить к нескольким задачам с явными соответствиями; число источников и импортов не является порогом качества. Сравнение описывает причину, компромиссы и содержательное различие. Первый по порядку результат может победить после такого сравнения, но не освобождается от него.

Одинаковое положение в макете не запрещает содержательно разный UX, набор, материал или техническую основу; не выдумывай новую компоновку ради сравнения стандартных controls. Если из изученного известно, что кандидаты отличаются только косметикой одного решения, можно указать одинаковое `candidates[].cosmetic_variant_of`: такой дубль не считается альтернативой. Это узкая объявленная группировка, не автоматический анализ визуального сходства; не ставь её всем компонентам одной библиотеки или вариантам с разным поведением.

Узкие маршруты `exact_user_reference` и `current_project_basis` допускают отсутствие нового поиска/второго кандидата в порученных границах. `closure.basis` содержит `type`, `reference`, `text`: для точного поручения — `prompt|answer`, для актуальной основы этого продукта — `project`. Оба требуют подробного изучения выбранного материала. У current_project_basis также требуется фактический `same_project`; заготовка другого бренда не является этим исключением. Нет новой ресурсной задачи в local — нет обязанности создавать такую запись.

При недостаточности оснований `closure:{status:"unresolved",reason:"..."}` оставляет пробел независимо от готовности собственного предварительного кода. В старой записи без следа не выдумывай прошлые поиски: отметь ограничение и заново исследуй затронутую задачу при её изменении. Не стирай сохранённые прежние ответы или несвязанные результаты.

Статусы `comparison_recorded` и `scoped_basis_recorded` подтверждают только структуру объявленного отбора. Валидатор не умеет установить истинность запроса, качество визуального анализа, семантическое соответствие тегов, достаточность исследования или добросовестность исключения. Он не выполняет поиск и не заменяет сравнение реальных материалов. Непустые формальные фразы не делают поверхностный подбор тщательным.

## Проверка самого инструмента

`python -m unittest discover -s tests -p test_resource_pipeline.py -v` запускает изолированные fixtures: HTTP 200 shell/metadata, missing dependencies/helpers, транзитивный граф, unsafe paths/collisions/overwrite, receipt/cache integrity, отсутствие выполнения package scripts, rejected/open/unknown решения, свежесть наблюдений и оба provenance-маршрута. Fixtures не требуют сети и не оценивают дизайн. Реальный публичный fetch подтверждает канал лишь в момент запуска; он не устанавливает компонент в пользовательский проект и не меняет установленный скилл.
