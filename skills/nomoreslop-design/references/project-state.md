# Актуальное содержание, решения и свидетельства

Читай при новом проекте, продолжении после перерыва и изменении определяющего участка. Небольшая правка использует затронутые записи; не требует нового брифа. Структура помогает продолжать работу и обнаруживать пробелы, но не удостоверяет истинность самоотчёта или качество дизайна.

## Где хранить

Используй принятый закрытый каталог проекта; при отсутствии — `.local/nomoreslop/`, исключённый из коммита и публикации. `content.md` содержит факты с источниками, материал и **точные тексты** с действиями/существенными состояниями. Актуальные решения сохраняй в одном `design-state.json`; имеющийся `design-state.md` также подходит, если точные проверки выполняются вручную. Не веди два независимо редактируемых источника правды. Машинная проверка ниже работает с JSON, Markdown не объявляется ею проверенным.

Последняя правка дополняет решения и ограничения, а не заменяет их списком новых задач. При переносе рабочей копии перенеси действующее содержание, происхождение и ссылки на необходимые свидетельства. Восстановление из старой соседней копии отмечай как восстановление, неизвестное не додумывай.

## Минимальное состояние

Скрипт `scripts/design_state.py init --output <project>/.local/nomoreslop/design-state.json` создаёт **незакрытый шаблон**. Для локального исправления есть `--mode local`. Файл не перезаписывается. Если запись уже есть, обнови её по фактическим решениям, не создавай новое пустое состояние вместо истории.

Основные поля:

- `schema_version: 1`, `mode: new|redesign|local`, `content_path` относительно проекта.
- `intent`: посетитель и результат (`visitor`), доступный материал (`material`), наблюдаемый характер выбранного решения (`distinctive_result`). Последнее может описывать уместное спокойное рабочее решение; оно не требует эффектов ради числа.
- `brief`: существенные решения, состояния и основания. `required` означает относящуюся к задаче значимую неизвестную, не все пункты универсальной анкеты.
- `research_profile`: заданные/выведенные теги общего направления с основанием; у выбранных решений `research` сохраняет реальные запросы, внутреннее изучение, сравнение и закрытие по [протоколу отбора](resource-selection.md) и [машинной схеме](resource-pipeline.md#проверка-глубины-отбора).
- `decisions`: очередь значимых участков, подобранные ресурсы и фактическое применение по [ресурсному конвейеру](resource-pipeline.md).
- `checks`: общие проверки. У отдельных `decisions` могут быть собственные `checks` той же формы.
- `next`: ближайший незавершённый результат и ограничения.

Пример закрытого решения:

```json
{
  "id": "palette",
  "topic": "Цветовые отношения",
  "required": true,
  "status": "delegated",
  "basis": {
    "type": "delegation",
    "reference": "Ответ пользователя на вопрос о палитре",
    "text": "Палитру выбери сам, без красного"
  }
}
```

Состояния: `given`, `delegated`, `open`, `proposed`, `not_applicable`. Для закрытого решения нужны тип основания `prompt|answer|delegation|project`, реальная ссылка/идентификатор и точное относящееся содержание. Предложение агента не согласовано до ответа, если выбор не поручен ему. Полное делегирование разрешает творческий выбор; оно не создаёт неизвестные факты о бизнесе. Поле с произвольным текстом не доказывает действительность ответа — это проверяется по переписке/материалу.

## Свидетельство проверки

Для значимого вывода записывай:

```json
{
  "id": "gallery-wide",
  "kind": "visual",
  "status": "unverified",
  "required": true,
  "files": {},
  "environment": {},
  "action": "",
  "observation": "",
  "evidence": [],
  "reason": "Настоящий просмотр текущей композиции ещё не выполнен"
}
```

`kind`: `build`, `copy`, `function`, `visual`, `source_property`. `status`: `required`, `passed`, `failed`, `unverified`, `not_applicable`. Неприменимость и невозможность проверки требуют конкретной причины. У `passed` должны быть фактическое действие, наблюдение, ссылки на свидетельства, среда и хеши **относящихся файлов текущей версии**. Ссылки на изображения/логи сами по себе не подтверждают их содержание.

Для настоящего визуального просмотра укажи `environment.method: browser-render|native-render|device-render` и `viewport` либо `device`. Happy-dom, исходники и условные размеры не являются таким просмотром. Один кадр подтверждает только его состояние; движение и обратный ход проверяются действием.

Получить хеши выбранных файлов:

```text
python <skill>/scripts/design_state.py snapshot --project <project> --path dist/index.html --path dist/app.js --path dist/style.css
```

Скрипт хеширует только явно названное. Включай действительные CSS, шрифты, изображения и связанные скрипты, от которых зависит проверяемое свойство; не исключай зависимость, чтобы сохранить старую отметку. Он не строит полный граф влияния автоматически. При `--output` создаётся только новый явно указанный JSON, входные файлы не меняются.

Проверка актуальности:

```text
python <skill>/scripts/design_state.py check <state.json> --project <project> --stage composition
python <skill>/scripts/resource_pipeline.py coverage <state.json> --project <project>
```

Первый инструмент проверяет объявленный бриф и актуальность относящихся хешей. Второй — структуру подбора и применения ресурсов. Они не исполняют проект и не оценивают выразительность. Результат `structurally_consistent` означает согласованную запись, **не готовый хороший интерфейс**. Открытые обязательные проверки, `proposed` и устаревшие хеши остаются незавершёнными; исправь запись/результат по факту, не переименовывай статус ради зелёного вывода.

## После изменения

Пересмотри зависимые решения и проверки: новый текст — редактуру и размещение; новая сцена — смысл, источник, движение и рендер; другая геометрия управления — координаты и состояния. Повтори относящийся путь на текущей версии. Локальный отступ не обнуляет весь бриф и неподвижные части проекта. Недоступный браузер не мешает независимой работе, но визуальный результат остаётся `unverified`; публикация не закрывает его.
