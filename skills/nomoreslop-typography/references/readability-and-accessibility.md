# Читаемость, адаптация и доступность текста

Читай при проектировании текстовой системы, жалобах на мелкий или бледный текст, адаптиве, формах, смене темы и проверке готового интерфейса. Выбирай относящуюся ветку: локальная правка подписи не требует нового исследования всего каталога шрифтов. Покрытие локалей, shaping и фактически использованный файл проверяются по [font-validation.md](font-validation.md); этот документ проверяет условия чтения и работы с текстом.

## Что считается требованием

- **Критерий A/AA** — измеримый критерий WCAG указанного уровня, с его областью и исключениями. Нормативен [текст WCAG 2.2](https://www.w3.org/TR/WCAG22/); страницы Understanding объясняют его применение и сами не являются дополнительными требованиями.
- **Критерий AAA** — отдельная более строгая цель. Не выдавай её за условие AA и не объявляй весь проект AAA по одной проверке.
- **Практика навыка** — профессиональное решение для конкретной аудитории, языка, роли и экрана. Диапазон стартовых настроек не доказывает доступность и не заменяет проверку.

Проверки ниже покрывают типографические риски, а не весь WCAG. Результат формулируй по проверенному критерию, состоянию, локали и окружению. «Контраст этой пары 5.2:1» и «эта форма проверена при увеличении 200%» точнее недоказанного «сайт полностью доступен».

## Маршрут по проблеме

| Сигнал | Нужная ветка |
| --- | --- |
| Текст маленький, утомляет, теряется рядом с графикой | Масштаб по роли → контраст → реальный рендер |
| Мелкий футер, нечитаемые подписи/ошибки | Масштаб по роли → формы и состояния → увеличение |
| Набор распадается на телефоне или после увеличения | Reflow → переносы → пользовательские интервалы |
| Белый текст исчезает на изображении, меняется тема | Контраст → подложки и темы → системная палитра |
| Заголовки красивые, но структура непонятна | Семантика → длина строки → когнитивная ясность |
| Desktop/mobile приложение с настройкой размера текста | Ветка целевой платформы; web-проверка сама по себе её не закрывает |

## Масштаб по роли: маленький текст не должен оплачивать композицию

**Сигнал.** Важное содержание приходится разглядывать; hero огромный, а навигация, пояснения и футер выглядят как служебный шум; длинный текст уменьшен ради одной строки или фиксированной карточки.

**Решение — практика навыка.** Назначь роль и условия чтения до размера: длительное чтение, быстрое сканирование, выбор действия, данные, вторичная справка. Оцени x-height, ширину знаков, толщину штриха, апертуры, язык, дистанцию и плотность. Одинаковое CSS-число у двух гарнитур не означает одинаковый воспринимаемый масштаб. В паре display/body сравни фактические строки в своих ролях, а не specimen одной величины.

Сначала исправляй ширину контейнера, перенос, структуру или избыток содержания; затем настраивай размер. Не используй `transform: scale(...)`, отрицательный tracking или экстремально узкий шрифт как способ втиснуть обязательную подпись. Отдельная крупная редакционная надпись может быть плотной и выразительной; связный текст и действия не должны наследовать её настройки автоматически.

**Проверка.** На действительном масштабе страницы прочитай основной абзац, навигацию, подписи к работам, цены, футер, label, ввод, помощь и ошибку. Сравни их с общим размером композиции и ближайшими действиями. Возьми длинные реальные значения; проверь различимость цифр и значимых символов. Не оценивай только увеличенный screenshot или изолированный компонент.

**Граница.** У WCAG нет универсального обязательного минимума `16px` для любого текста. Значение `16px` может быть отправной точкой конкретного web-body, но не разрешением сделать любой интерфейс читаемым по декларации. Небольшие действительно вторичные метаданные допустимы при подтверждённых условиях чтения. Контакт, юридическое условие покупки, критичная помощь и ошибка не становятся второстепенными из-за расположения внизу.

### Футер, плотный UI и площадь действия

**Сигнал.** Футер превращён в полоску микротекста, названия работ выглядят как подписи к thumbnail, заметность контакта уступает декору.

**Решение.** Раздели содержимое по задаче: следующий шаг и контакты; навигация; действительно вторичные сведения. Сохрани видимую иерархию без общего уменьшения всей зоны. В плотной таблице сначала используй логическую группировку и подходящее представление данных; плотность сама по себе не оправдывает исчезновение текста.

**Проверка.** Найди контакт и нужный раздел без увеличения, прочитай условие, выбери соседние ссылки пальцем и клавиатурой. Проверь переносы в каждой поддержанной локали.

**Граница.** Размер букв и площадь нажатия — разные свойства. Увеличенный padding не исправляет нечитаемую надпись, крупный текст не гарантирует достаточную цель. Для web отдельно применяй [SC 2.5.8 Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) с его исключениями; не переноси его значения на кегль.

## Контраст: точные пороги и их пределы

**Сигнал.** Бледные вторичные подписи, текст на акцентном фоне или ошибка «на глаз нормально».

**Решение — AA, SC 1.4.3.** Для текста и изображений текста требуется не менее **4.5:1**; для крупного текста — **3:1**. Крупный: от **18 pt** обычного или **14 pt** жирного (bold); при соотношении CSS `1pt = 4/3px` это **24 CSS px** и примерно **18.67 CSS px**, а не произвольные 18px. Для CJK учитывай эквивалентный размер по определению large-scale. Проверяй реальное начертание. Значение 4.499:1 не округляй до прохождения.

**Проверка.** Рассчитай пару foreground/background во всех показанных состояниях, включая placeholder, hover и focus. Сохрани цвета, размер, вес и отношение. Порог относится к заданным цветам, а не к самым светлым пикселям сглаженного контура. При тонких штрихах усиливай рисунок или контраст и оцени реальный рендер: формальное прохождение не обещает удобного чтения.

**Граница.** У критерия есть исключения: логотипы/brand-name text, неактивные контролы и определённый incidental text. Они не освобождают обычный текст бренда, footer или вспомогательное пояснение. [W3C: SC 1.4.3, область, крупный набор и тонкие штрихи](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).

### Прозрачность, изображения и темы

**Сигнал.** В токенах цвета проходят, в готовом интерфейсе подпись исчезает; белый текст работает только на одном кадре видео.

**Решение — практика навыка.** Проверяй итоговое наложение: alpha у цвета, `opacity` родителя, overlay, градиент, изображение, blending и меняющийся фон. `opacity` применяется ко всему элементу вместе с содержимым; затемнение одной подложки задавай отдельно, когда текст должен оставаться непрозрачным. [MDN: поведение opacity](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/opacity).

Если фон непредсказуем, обеспечь стабильную область чтения: подложку, scrim, отдельную текстовую зону или ограничение визуала. Проверяй наименее благоприятную область под буквами и состояния движения, а не средний цвет картинки. Тень или blur не считаются доказательством контраста. Для светлой и тёмной темы проверь собственные пары текста, фона, ссылок, ввода, выделения и состояний; инверсия палитры не закрывает проверку.

**Проверка.** Посмотри реальный контент, смену кадра/слайда, crop на узком экране, загрузку/ошибку изображения и обе темы. Автоматический анализ может не распознать сложную подложку: отметь ручную проверку или открытый риск.

**Граница.** «Чёрный на оранжевом» не является универсально запрещённой парой. Проблемой могут быть конкретная яркость, мелкий размер, тонкое начертание или большой насыщенный фон. Исправление должно отвечать наблюдаемой причине, сохраняя цветовую идентичность.

## Иерархия должна существовать и вне визуального макета

**Сигнал.** Визуальные заголовки набраны `div`, уровень `h3` выбран из-за CSS-размера, строка выглядит ссылкой, но ею не является.

**Решение.** Отдели смысловую роль от оформления. Структура и связи, переданные расположением и типографикой, должны быть программно определимы либо доступны текстом: заголовки, списки, таблицы, label и группировка формы. Для web используй подходящие нативные элементы; CSS-класс задаёт вид независимо от ранга. Уровень заголовка выбирай по структуре содержимого, не по желаемому кеглю. [W3C: SC 1.3.1 Info and Relationships](https://www.w3.org/WAI/WCAG22/Understanding/info-and-relationships.html).

Заголовок и label должны предсказывать тему или назначение. Краткое название достаточно, если оно понятно в контексте; постоянный поясняющий абзац справа не исправляет пустое название. Этот критерий проверяет описательность, а правильную разметку — отдельно. [W3C: SC 2.4.6 Headings and Labels, AA](https://www.w3.org/WAI/WCAG22/Understanding/headings-and-labels.html).

**Проверка.** Просмотри дерево доступности и порядок чтения, затем прочитай список заголовков отдельно от декоративного оформления. Проверь связь названия с разделом, label с полем, заголовка таблицы со значениями. Автоматический список тегов не доказывает, что названия осмысленны.

**Граница.** Плакатная надпись не обязана быть заголовком, а маленький заголовок не теряет смысловую роль. Не навязывай одинаковую типографическую лестницу каждому бренду. Исправляй связь и чтение, сохраняя композиционный замысел.

## Длина строки, ритм чтения и когнитивная ясность

**Сигнал.** В абзаце трудно найти следующую строку; текст растянут на всю ширину desktop; центрирование и капитель делают чтение медленным.

**Решение — практика навыка.** Для связного Latin/Cyrillic текста можно начать сравнение с колонок около **50–75 знаков в строке**, затем проверить настоящую гарнитуру, язык, размер и задачу. Это рабочая эвристика, не норма AA и не математический допуск. Узкая UI-подпись, стихи, код, крупный слоган и таблица имеют другие задачи. `ch` измеряет метрику определённого знака, не гарантирует точное количество реальных символов в строке.

Для длинного чтения предпочитай выравнивание по началу строки соответствующего направления. Проверь ровность межсловных пробелов; полная выключка, длинные центрированные абзацы и набор сплошными прописными требуют предметного обоснования. Разделяй темы абзацами, располагай действие после нужных для него сведений. Не добавляй декоративные пояснения, которые повторяют заголовок, и не удаляй полезную помощь ради «антислопа».

**Проверка.** Прочитай непрерывно несколько настоящих абзацев; проверь длинные слова, короткие последние строки, списки и соседство с иллюстрациями. В локализации проверь реальные языковые правила переноса и направление, а не только число знаков. Не применяй Latin-tracking к связанным письменностям; диакритики и сложный shaping требуют отдельной проверки.

**Граница — AAA.** [SC 1.4.8 Visual Presentation](https://www.w3.org/WAI/WCAG22/Understanding/visual-presentation.html) описывает доступный механизм изменения представления блоков текста, в том числе ширину до 80 знаков/глифов, для CJK — 40, и отсутствие полной выключки. Это не универсальные исходные значения AA. Учитывай особенности письменности; не превращай один показатель в оценку всей читаемости.

Трудность понимания также не сводится к кеглю: термины, сокращения, структура и предварительные знания аудитории проверяются вместе с writing. [SC 3.1.5 Reading Level](https://www.w3.org/WAI/WCAG22/Understanding/reading-level.html) — критерий **AAA** с определённой областью; метрика сложности для английского не является универсальным тестом русского, казахского или другого языка.

## Увеличение текста: проверяй механизм пользователя

**Сигнал.** Увеличение обрезает label/кнопку, фиксированный header закрывает содержание, responsive-формула уменьшает текст при zoom.

**Решение — AA, SC 1.4.4.** Текст должен увеличиваться до **200%** без потери содержания и функций через поддерживаемый пользовательский механизм, без assistive technology. Критерий исключает субтитры (captions) и изображения текста. Контейнеры и действия должны принимать выросший набор; не нейтрализуй увеличение viewport-формулой или сменой breakpoint. Не блокируй пользовательский zoom настройками viewport; проверь поведение поддержанных браузеров.

**Проверка.** В настоящем браузере проверь 100%, промежуточный масштаб и 200% относительно исходного текста. Проверь все затронутые роли и контролы, overlays и доступ к полному содержанию. `transform: scale`, screenshot resize и подстановка большого `font-size` не воспроизводят browser zoom. При необходимости отдельно проверь пользовательский размер текста; поддержка всех механизмов сразу не является буквальным требованием этого критерия. [W3C: SC 1.4.4 Resize Text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html).

**Граница.** Использование `rem` не доказывает прохождение, а наличие `px` само по себе не доказывает провал. Нужны поведение и результат. Если реальный механизм не проверен, оставь `zoom_unverified`; продолжай доступную подготовку, не заявляя успешный тест.

## Reflow: узкий viewport и увеличение — разные проверки

**Сигнал.** Страница требует горизонтального движения для чтения обычной строки, скрывает меню/форму после zoom, сохраняет широкую desktop-сетку.

**Решение — AA, SC 1.4.10.** Для вертикального чтения требуется отсутствие потери содержания/функций и двумерного scrolling при ширине **320 CSS px**. Для содержимого, рассчитанного на горизонтальное scrolling, проверяется высота **256 CSS px**. Размеры относятся к CSS viewport, не физическим пикселям устройства.

**Проверка.** Проверь узкую раскладку и реальное увеличение: viewport 1280 CSS px при 400% соответствует ширине 320 CSS px. Подтверди фактический viewport; один мобильный screenshot не подтверждает 200% resize. Сохрани доступ к действиям, содержанию раскрытий и фокусируемым элементам.

**Граница.** Исключение относится только к частям, где двумерная раскладка необходима для смысла/использования: например, карте, диаграмме или таблице данных. Оно не освобождает всю страницу; текст отдельной ячейки также должен адаптироваться, когда двумерность ему не нужна. [W3C: SC 1.4.10 Reflow и исключения](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html).

### Длинные значения и обрезание

**Сигнал.** Адрес, email, название проекта или перевод выталкивает колонку; ellipsis скрывает значимое различие объектов.

**Решение — практика навыка.** Разреши перенос в подходящем контейнере и проверь ограничения flex/grid. Для неразрывных идентификаторов используй адресную стратегию переноса, а не глобальный `word-break: break-all` для прозы. Различай словарные переносы, перенос URL и искусственный разрыв слова. Не вставляй неразрывные пробелы по всему тексту и жёсткие `<br>` ради единственного desktop-снимка.

**Проверка.** Используй реальные длинные значения и сравни объекты с одинаковым началом. Если усечение необходимо, полное значение должно быть доступно понятным действием также с клавиатуры и touch, с сохранением возможности выполнить задачу. Один `title` или mouse-only hover не является достаточной стратегией продукта.

**Граница.** Усечение не запрещено всегда. Для компактного списка оно может быть обосновано, если не уничтожает идентификацию и полный текст доступен. Конкретные исключения resize/text-spacing оценивай по соответствующему критерию; не считай любое скрытие автоматически допустимым.

## Пользовательские интервалы: выдержать изменение, а не навязать шаблон

**Сигнал.** Изменение интервалов обрезает подписи, сдвигает строки поверх друг друга или прячет кнопку.

**Решение — AA, SC 1.4.12.** Для технологий разметки, поддерживающих эти свойства, не должно быть потери содержания/функций при одновременном пользовательском изменении следующих свойств, без изменения остальных:

| Свойство | Проверяемое значение |
| --- | --- |
| Высота строки | не менее 1.5 размера шрифта |
| Отступ после абзаца | не менее 2 размеров шрифта |
| Межбуквенный интервал | не менее 0.12 размера шрифта |
| Межсловный интервал | не менее 0.16 размера шрифта |

**Проверка.** Примени пользовательское переопределение ко всем относящимся ролям, затем открой формы, tabs и раскрываемые области. Проверь clipping, наложение и доступ к полному тексту. Применяй нужные свойства к реальным абзацам, а не только к выбранному demo-блоку.

**Граница.** Это тест переносимости, **не обязательные исходные настройки** и не требование встроенного переключателя. Для языков/письменностей, где свойство не применяется, проверяются применимые свойства. Изображения текста и canvas не обязаны перестраиваться по этому критерию. [W3C: SC 1.4.12 Text Spacing](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html).

## Формы, ошибки, ссылки и скрытые состояния

**Сигнал.** Поле теряет название после ввода; ошибка красная и почти незаметна; текст ссылки отличается только оттенком; доступное имя кнопки не совпадает с надписью.

**Решение.** У поля сохраняется читаемый label. Placeholder служит примером, когда нужен, и не заменяет постоянное название. Формат/ограничение указывай до ошибки, если они действительно нужны; свяжи помощь с соответствующим полем. Не превращай борьбу с избыточным microcopy в удаление необходимых инструкций. [WAI: инструкции и placeholder в формах](https://www.w3.org/WAI/tutorials/forms/instructions/).

Автоматически обнаруженная ошибка должна указывать ошибочный элемент и описываться текстом. Назови причину и, когда уместно, способ исправления; не уменьшай её ради компактной формы. Проверь введённое значение, ошибку и повторную отправку. [W3C: SC 3.3.1 Error Identification](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html).

Цвет не должен быть единственным визуальным способом передачи действия или состояния. Для ссылки внутри текста используй устойчивый различимый признак, например подчёркивание; для ошибки — также текст/иной признак. Не требуй одинакового подчёркивания у всей явно оформленной навигации независимо от контекста. [W3C: SC 1.4.1 Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html).

Если видимый label содержит текст, accessible name контрола содержит этот текст; предпочтительно начинать имя с него. Не подменяй «Отправить» скрытым названием «Запрос коммерческого предложения» ради формального ARIA. [W3C: SC 2.5.3 Label in Name](https://www.w3.org/WAI/WCAG22/Understanding/label-in-name.html).

**Проверка — практика навыка.** Пройди пустую, заполненную, ошибочную, loading/success и недоступную ветки, если они есть. Просмотри focus, открытый tooltip/popover и локализованные label. Проверь, что человек находит и понимает изменение, а важная помощь не доступна только hover. Для icon-only действий отдельно проверяются понятность и accessible name; не добавляй мелкое пояснение к каждой знакомой иконке автоматически.

**Граница.** Неактивный контрол имеет исключение из требования контраста SC 1.4.3, но это не рекомендация скрыть нужное объяснение его состояния. Текст причины недоступности оценивай как обычный читаемый текст. Контраст букв, заметность границы контрола, видимость focus и площадь действия — отдельные проверки.

## Пользовательская палитра и нативные поверхности

### Forced colors и системные переопределения

**Сигнал.** В системном контрастном режиме исчезают надпись, граница, ссылка или выделение.

**Решение.** Позволь браузеру применять пользовательскую палитру. Не ставь `forced-color-adjust: none` на весь интерфейс ради сохранения бренда. Адресно исправляй потерянные признаки системными цветами и подходящими border/outline. Текст на изображении и визуальные различия, зависящие от shadow/gradient, требуют отдельного просмотра. [W3C: CSS Color Adjustment, forced colors](https://www.w3.org/TR/css-color-adjust-1/#forced), [MDN: поведение forced-colors](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/forced-colors).

**Проверка.** Проверь используемый браузер в действительном режиме пользователя или явно названной эмуляции: чтение, ссылки, поля, выделение и focus. Различай эмуляцию свойства и полную системную среду.

**Граница.** Пользовательская палитра может намеренно отличаться от брендовой. Не пытайся восстановить в ней обычный арт-дирекшн. Локальное исключение для существенного цвета изображения/образца требует конкретной причины и проверки окружающего текста.

### Desktop и mobile приложения

**Сигнал.** Web-specimen проверен, но приложение обрезает текст при системном увеличении; custom control не наследует native-поведение.

**Решение.** Сначала определи платформу и технологию. Используй её текстовые роли, масштабирование и доступные нативные контролы; проверь собственные шаблоны отдельно. Для Android учитывай `sp` и нелинейное масштабирование: не воспроизводи его умножением на одну константу. Для Windows проверь системное увеличение текста и layout custom controls. [Android Developers: масштабирование до 200% и проверка приложения](https://developer.android.com/about/versions/14/features#non-linear-font-scaling), [Microsoft: text scaling](https://learn.microsoft.com/en-us/windows/apps/develop/input/text-scaling).

**Проверка.** В целевой среде включи поддержанные увеличенные размеры текста, проверь длинные значения, формы, toolbar, диалоги и настройки. Назови реальные платформу, версию и настройки.

**Граница.** CSS px, Android sp, Apple pt и Windows effective pixels не являются одной общей типографической шкалой. Не переносись с результатов web на native и не выдавай узкий браузерный viewport за тест мобильного приложения. Для Apple и других платформ изучи актуальное официальное руководство выбранной технологии; не сочиняй параметры по аналогии.

## Графика с текстом и выразительная типографика

**Сигнал.** Заголовок запечён в изображение ради шрифта, важная надпись существует только в canvas/WebGL, эффект scramble мешает чтению.

**Решение.** Когда нужное представление достижимо текстом, сохраняй текст вместо изображения текста. У [SC 1.4.5 Images of Text, AA](https://www.w3.org/WAI/WCAG22/Understanding/images-of-text.html) есть исключения для настраиваемого и существенного представления, включая логотип. Снимок работы или значимое изображение с текстом оценивается по своей функции, а не автоматически как обычный абзац.

**Проверка — практика навыка.** Значимое содержание доступно и в итоговом состоянии эффекта; чтение не требует поймать кадр. Сохрани корректное доступное текстовое представление без дублирования при озвучивании. Проверь увеличение и fallback при отключении/ошибке визуала. Состояния и управление анимацией передай в motion/design, не считая их закрытыми типографическим тестом.

**Граница.** Доступность не требует сделать каждую декоративную надпись body-шрифтом. Выразительный display, необычная композиция и брендовый рисунок сохраняются, если важный смысл и действие остаются читаемыми и доступными. Один alt не исправляет все проблемы текста, встроенного в графику.

## Как зафиксировать проверку без фиктивного «всё прошло»

В общей записи проекта сохрани только относящиеся результаты, без отдельной бюрократической документации для каждой подписи:

| Проверка | Что записать |
| --- | --- |
| Масштаб и реальный набор | Роль, локаль, фактически использованный face/вес, проблемная строка и наблюдение |
| Контраст | Пара с учётом подложки/состояния, отношение, применённый порог и причина исключения при наличии |
| Resize | Браузер/платформа, настоящий механизм, 100% → промежуточное → 200%, результат затронутых сценариев |
| Reflow | Фактический CSS viewport и/или zoom, сохранённые действия, локальное 2D-исключение |
| Text spacing | Применимые свойства, одновременное переопределение, проверенные состояния |
| Семантика/формы | Читаемый порядок, связь label/help/error, название действия, реальные состояния |
| Темы/системные настройки | Какие темы и настройки проверены, какая часть была только эмулирована |
| Оставшееся | `render_unverified`, `zoom_unverified`, непроверенная локаль/платформа или конкретный риск |

Для собственного интерфейса используй реальный браузерный или native-рендер. DOM/CSS-анализ и автоматический аудит находят часть дефектов, но не подтверждают удобство чтения, правильный glyph, смысл заголовка или все состояния. Внешние материалы продолжай изучать программно по правилам навыка; собственный визуальный QA не разрешает browser/computer-use для поиска внешних референсов.

После изменения семьи, размера, веса, ширины, темы, текста или контейнера повтори затронутую проверку. Не начинай заново весь процесс без причины. Проверяй нормативные режимы отдельно; дополнительные сочетания zoom + пользовательские интервалы + длинная локализация являются полезной стресс-проверкой продукта, но не должны выдаваться за буквальную формулировку одного критерия.
