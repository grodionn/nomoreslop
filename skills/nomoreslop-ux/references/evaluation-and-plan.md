# Аудит, план исправления и приёмка

## Что считать доказательством

Разделяй наблюдённое препятствие, гипотезу причины, неизвестные условия и уже исправленный исторический случай. Укажи экран/состояние, доступные данные/роль/среду, действие и наблюдение. Из кода можно установить риск и некоторые логические дефекты, но нельзя объявлять рендер проверенным. Один кадр не показывает повтор, восстановление, поиск и реальные ограничения API.

Документарный разбор паттерна, экспертная оценка, пользовательское исследование, аналитика реальных действий, автоматический тест и физическое устройство — разные основания. Не выдумывай интервью/записи/heatmap. Эвристика помогает найти риск; улучшение конверсии, времени и ошибок требует соответствующей проверки.

## План работы по задаче

1. **Область:** объект аудита/исправления, существующий материал, сохранённые решения, поддержанные действия и границы прототипа.
2. **Ключевые задачи:** что человек должен понять/найти/сравнить/сделать. Отдельно существенные роли, ввод и первая/повторная работа.
3. **Покрытие:** какие пути, данные, состояния и среды дают решающие различия; что можно проверить сейчас и что нет.
4. **Проблемы:** наблюдение → влияние на задачу → вероятная причина/уверенность → исправление и зависимости → приёмка.
5. **Порядок:** сначала сохранность, доступ, опасные неверные действия и блокеры; затем успешность/понятность задачи, частые затраты, общая система и локальная полировка.
6. **Выполнение:** в поручении на исправление реализуй и проверь; в запросе на аудит отдай план. Переход между этими этапами не создаёт новую авторизацию на внешние действия.
7. **Итог:** выполнено, реально подтверждено, осталось открытым и следующий шаг. Не выдавай общий «UX стал лучше» без основания.

Для маленькой правки достаточно причины, решения и проверки, без полного отчёта. Используй существующее состояние проекта; одна цепочка решений полезнее нескольких конкурирующих журналов.

## Карточка проблемы

- Где / задача / роль / состояние.
- Наблюдение и способ его получения; причина отдельно с уровнем уверенности.
- Последствие: блокирует, рискует потерей/неверным действием, замедляет/затрудняет либо локально мешает.
- Частота/охват известны или остаются неизвестными; не подставляй выдуманные проценты.
- Решение в пределах задания, существенный компромисс и владелец.
- Проверка: начальное условие → действие → ожидаемый результат → метод и незакрытое.

Не оценивай одним баллом весь UX. Для приоритета сопоставляй последствия, охват/частоту и уверенность; один необратимый редкий сбой может быть важнее частой косметики. Числовая severity-шкала допустима с определениями, не обязательна.

## Приёмка и регрессия

Когда неизвестна сама модель задачи, выбирай относящийся способ исследования: разговор/наблюдение для контекста, проверка названий/групп и tree-task для поиска раздела, сценарная usability-проверка для поведения, реальные логи/аналитика для частоты и результата. Не объявляй этот выбор проведённым исследованием; гипотезу, исходные данные и критерий фиксируй отдельно. Малой обратимой правке не нужна обязательная исследовательская программа. Сравнивай варианты на одинаковой задаче/материале, не только по субъективной привлекательности.

Для выбранной задачи проверь success, важный отказ, изменение решения и возврат. Представительные данные: длинное/разное, ноль/неизвестное, несколько страниц/выборка, частичный результат/конфликт. Выбор зависит от риска, не фиксированного количества примеров. Визуально чистая пустая база не подтверждает наполненную, а большой synthetic dataset не доказывает удобную структуру.

Проверь реальные ширину/высоту/масштаб вокруг относящихся переломов. Выполни существенное доступными способами ввода; IME, screen reader и физическое touch подтверждаются подходящим методом. Видимый/доступный focus, порядок и фон overlay проверяются действием. Производительность измеряется в названной среде по узкому месту; выбор transform/opacity не обещает FPS.

Для интегрированного сценария проверь нужные контракты UI/API в тестовой среде и роли, не только мок. Поздний ответ, повторный submit, refresh и истечение не должны молча подменять результат/ввод. Не отправляй реальные сообщения, платежи и другие внешние действия ради UX-проверки без нужного разрешения.

После общей правки установи зависимые экземпляры и состояния и повтори затронутое. Не сбрасывай весь бриф и не прогоняй несвязанные проверки без причины. Открытые пункты храни по поверхностям/версиям; восстановление браузера — повод закрыть накопленный визуальный долг, а не объявить всё проверенным одним снимком.
